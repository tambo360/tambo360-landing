# Decisiones técnicas — tambo360-landing

Registro append-only. Modo elegido: **propuestas** (el usuario pidió avanzar en autonomía hasta un bloqueante; los detalles los decide el agente, etiquetados, y el usuario objeta lo que no le sirva).

- **QT-01** ¿Framework y CSS? → Astro 7.3.5 + Tailwind CSS 4.3.3 vía `@tailwindcss/vite`. · usuario (pedido inicial); versiones investigadas en npm el 2026-10-05.
- **QT-02** ¿Dónde se guardan las inscripciones? → Cloudflare D1 (SQLite). · usuario (Q-31).
- **QT-03** ¿Dónde se aloja la landing? → Cloudflare Workers con `@astrojs/cloudflare` 14.3.3 (peer `astro ^7.2.0`). Se deduce de QT-02: D1 se accede por binding desde un Worker. · agente, dentro del alcance.
- **QT-04** ¿Páginas estáticas o en servidor? → `output: 'static'`; solo el endpoint de inscripción se renderiza a pedido (`export const prerender = false`). Es lo que da mejor performance y SEO. · agente, dentro del alcance; capacidad investigada en docs.astro.build/en/guides/integrations-guide/cloudflare/ el 2026-10-05.
- **QT-05** ¿Cómo accede el endpoint a D1? → `import { env } from 'cloudflare:workers'`; `env.DB.prepare(...).bind(...).run()`. `Astro.locals.runtime` fue eliminado en esta versión del adaptador. · investigado: docs de Astro (Cloudflare) y developers.cloudflare.com/d1/get-started/, 2026-10-05.
- **QT-06** ¿Cómo se optimizan las imágenes? → `imageService: 'compile'`: se transforman con sharp en el build (AVIF/WebP, varios anchos). El default del adaptador (`cloudflare-binding`) transforma en runtime con Cloudflare Images, que tiene costo y no hace falta en páginas estáticas. · investigado (docs Astro Cloudflare, 2026-10-05) + agente.
- **QT-07** ¿Esquema de la inscripción? → Tabla `waitlist` con teléfono único (cumple RN-inscripcion-repetida), migraciones versionadas en `migrations/` aplicadas con `wrangler d1 migrations`. · agente, dentro del alcance.
- **QT-08** ¿Protección contra spam en el formulario? → Campo trampa (honeypot) + validación en el servidor. Sin captcha de terceros para no sumar peso ni fricción. · agente, dentro del alcance.
- **QT-09** ¿El formulario funciona sin JavaScript? → Sí: es un `<form method="post">` real hacia el endpoint, que redirige a una página de resultado; con JS se mejora enviando por `fetch` y mostrando el resultado en línea. · agente, dentro del alcance.
- **QT-10** ¿Configuración de WhatsApp, dominio y redes? → Un solo archivo de configuración del sitio (`src/config/site.ts`). WhatsApp vacío = el botón no se muestra (RN-whatsapp-a-confirmar). · agente, dentro del alcance.
- **QT-11** ¿Dominio? → `[TO-DEFINE]` (Q-35). Mientras tanto se usa `https://tambo360.com.ar` como valor provisorio en la configuración; canonical, sitemap y OG dependen de él.
- **QT-12** ¿Qué niveles de test automatizado se escriben? → propuesta: unitarios de la validación del formulario con Vitest; sin E2E; el resto se verifica con build + Lighthouse. Sin respuesta del usuario: hasta entonces no se escriben tests automatizados.
- **QT-11** (actualización 2026-10-05) El usuario propone `tambo360.vercel.app`. Objetado: lo ocupa la app y es de Vercel; la landing corre en Cloudflare Workers. Sigue abierto → QT-14.
- **QT-12** (respuesta 2026-10-05) Tests unitarios con Vitest. · usuario. Reemplaza la propuesta anterior de QT-12.
- **QT-13** ¿Dónde vive el `database_id` de D1? → El usuario pide que no esté en el archivo de configuración sino en una variable de entorno. · usuario. Investigado 2026-10-05: wrangler no interpola variables de entorno en `wrangler.jsonc` (developers.cloudflare.com/workers/wrangler/configuration/, sin mención de interpolación) y la doc oficial no dice si los IDs son secretos; en el repo oficial, una persona del equipo de Cloudflare responde: "It's fine to have a public wrangler.toml and include values like KV namespace ids, account ids, bucket names etc." (github.com/cloudflare/workers-sdk/discussions/7115, leído 2026-10-05). Objeción registrada (agente): el ID no es una credencial —sin token de la cuenta no da acceso—, así que moverlo agrega un paso de generación sin ganar seguridad real. Se ejecuta como decisión del usuario: plantilla versionada + `wrangler.jsonc` generado desde la variable `D1_DATABASE_ID`.
- **QT-11** (actualización 2026-10-23) `https://tambo360.vercel.app` en `src/config/site-url.mjs` (QT-22): la app se muda a otro dominio, todavía sin definir (estimado `app.tambo360.vercel.app`; que Vercel permita un tercer nivel en vercel.app está sin confirmar, solo foros de la comunidad). `site.registerUrl` queda vacío y los botones de registro se ocultan (QT-23). · usuario. Cierra QT-14.
- **QT-25** (2026-10-23) ¿Cómo se verifica el sitio en Google Search Console? → Meta `google-site-verification` en `SEO.astro`, con el código en la variable de entorno `PUBLIC_GOOGLE_SITE_VERIFICATION` (vacía = sin meta). Método etiqueta HTML porque en `tambo360.vercel.app` no hay DNS propio. `import.meta.env` se reemplaza en el build (docs.astro.build/en/guides/environment-variables/, leído 2026-10-23): cambiarla requiere redeploy. · usuario, propuesta del agente.
- **QT-13** (actualización 2026-10-05) Reemplazada: el `database_id` queda en `wrangler.jsonc`. · usuario, tras ver que el ID no es una credencial.
- **QT-14** ¿Dominio de la landing? → [TO-DEFINE] Opciones: subdominio `workers.dev` de Cloudflare (gratis, sin cambios), proyecto aparte en Vercel (obliga a cambiar el adaptador y acceder a D1 por API con token) o dominio propio.
- **QT-15** ¿Dónde se aloja la landing? → Vercel con `@astrojs/vercel` 11.0.15; reemplaza QT-03, QT-05 y QT-06 (sin wrangler ni `wrangler.jsonc`; imágenes con sharp en el build, que es el comportamiento por defecto). · usuario, 2026-10-19. Consecuencia: QT-02 (D1) queda sin acceso; la base del formulario está `[TO-DEFINE]` (opciones: Turso/libSQL, D1 por API HTTP con token, Postgres en Neon) y hasta entonces el endpoint responde `error` (503) sin guardar. `migrations/` y `src/lib/waitlist-repository.ts` se conservan para la base que se elija.
- **QT-20** (2026-10-23) ¿A dónde van las inscripciones del formulario? → Se envían por mail con Resend; sin base de datos. Reemplaza QT-16 (HubSpot) y deja sin efecto la base `[TO-DEFINE]` de QT-15. · usuario.
- **QT-27** (2026-10-23) ¿A quién se manda el mail? → Solo al equipo; la persona no recibe mail (el formulario no pide email). · usuario.
- **QT-28** (2026-10-23) ¿Desde qué remitente? → `onboarding@resend.dev` por ahora, sin dominio verificado. · usuario. Investigado (resend.com/docs/api-reference/errors, leído 2026-10-23): con el dominio de prueba, enviar a otra dirección que la del dueño de la cuenta da 403 `validation_error` ("You can only send testing emails to your own email address"). Consecuencia: `RESEND_TO` tiene que ser la casilla de la cuenta Resend; para que llegue a otras casillas hay que verificar un dominio y cambiar `RESEND_FROM`.
- **QT-29** ¿Cómo lee el endpoint la clave y las direcciones? → `astro:env` con `RESEND_API_KEY`, `RESEND_FROM` y `RESEND_TO` como `context: 'server'`, `access: 'secret'`, importadas de `astro:env/server`; se cargan en Vercel (Production y Preview) y cambiarlas no requiere rebuild. Si falta alguna, el endpoint responde `error` (503) como hoy. · agente, dentro del alcance. Investigado 2026-10-23: los secretos "are not part of your final bundle" (docs.astro.build/en/guides/environment-variables/) y "private variables are validated at runtime only" (docs.astro.build/en/reference/configuration-reference/, `env.validateSecrets`); `@astrojs/vercel` 11.0.15 declara `envGetSecret: "stable"` (node_modules/@astrojs/vercel/dist/index.js:61, fuente del adaptador instalado).
- **QT-30** ¿SDK de Resend o API directa? → `fetch` a `POST https://api.resend.com/emails` con `Authorization: Bearer`, `Content-Type: application/json` y `User-Agent: tambo360-landing`; sin dependencia nueva. · agente, dentro del alcance. Investigado (resend.com/docs/api-reference/introduction y /emails/send-email, leídos 2026-10-23): sin `User-Agent` la API responde 403; éxito = 200 con `{ id }`.
- **QT-31** ¿Qué dice el mail? → Solo texto (sin HTML, así nada de lo que escribe la persona se interpreta). Asunto `Inscripción al piloto: <nombre>, <teléfono>`. Cuerpo: nombre, WhatsApp con enlace `https://wa.me/549<teléfono>`, rol, provincia y vacas con sus etiquetas (o "sin dato"), origen, fecha y hora de Argentina, y que aceptó la política de privacidad. Sin `reply_to` (no hay email de la persona). · agente, dentro del alcance.
- **QT-32** ¿Qué pasa si Resend falla? → Cualquier respuesta que no sea 2xx, error de red o más de 8 s sin respuesta (`AbortSignal.timeout`) = no se guardó: el endpoint responde `error` (503) y la persona ve el mensaje con WhatsApp (RN-inscripcion-falla). Se loguea el código de Resend, nunca los datos de la persona. Sin reintentos: la persona puede volver a enviar. · agente, dentro del alcance. Investigado (resend.com/docs/api-reference/errors, leído 2026-10-23): 429 por límite por segundo o cupo diario/mensual, 403 por dominio no verificado o clave inactiva, 5xx del servicio. Plan gratis: 100 mails por día y 3.000 por mes (resend.com/pricing, leído 2026-10-23); el día 101 la inscripción falla con ese mensaje.
- **QT-33** ¿Cómo se evita mandar dos veces el mismo envío (doble clic, reenvío del navegador)? → Encabezado `Idempotency-Key` = `inscripcion-` + SHA-256 del teléfono normalizado y los demás campos. El mismo envío idéntico dentro de 24 h no manda un segundo mail y responde igual; cualquier dato distinto manda otro. · agente, dentro del alcance. Investigado (resend.com/docs/dashboard/emails/idempotency-keys, leído 2026-10-23): la clave dura 24 h y, repetida, "our API will give the same response, without actually sending the email again"; con la misma clave y otro cuerpo responde 409, por eso la clave incluye el contenido.
- **QT-34** Sin base, ¿qué pasa con RN-inscripcion-repetida (detectar el mismo teléfono y decir "ya estabas") y RN-inscripcion-guardada (cada inscripción guardada con su fecha para contarlas)? → propuesta, a preguntar: Resend solo manda; no puede decir si un teléfono ya se anotó, y su registro de envíos dura 30 días en el plan gratis (resend.com/pricing, leído 2026-10-23), así que no sirve de registro. Choca con dos reglas acordadas: vuelve a discovery.
- **QT-35** ¿Dónde quedan los datos que pasan por Resend? → Investigado (resend.com/docs/dashboard/domains/regions, leído 2026-10-23): "All account data, including email metadata, logs, and API records, is stored in the United States" sin importar la región de envío. Consecuencia para u79: la política de privacidad nombra a Resend como encargado y la transferencia a Estados Unidos; entra en la revisión legal pendiente.
- **QT-34** (respuesta 2026-10-23) El mail es el registro: la bandeja de la cuenta Resend es donde se cuentan las inscripciones; un teléfono repetido manda otro mail y la persona ve `ok` (el equipo reconoce los repetidos por el teléfono en el asunto, QT-31); "guardada" pasa a ser "Resend aceptó el mail" (200 con `id`), que no garantiza que llegue a la bandeja. · usuario. Cambia RN-inscripcion-repetida, RN-inscripcion-guardada y RN-inscripcion-falla: se reescriben en la spec en u79. El estado `repetido`, `src/lib/waitlist-repository.ts` y `migrations/` quedan sin uso: se borran en u78.
- **QT-36** (2026-10-23) ¿Hace falta cargar `RESEND_FROM` y `RESEND_TO`? → No: solo `RESEND_API_KEY`. El remitente queda fijo en el endpoint (`Tambo360 <onboarding@resend.dev>`) y el destinatario es `site.email` (`t360.arg@gmail.com`), que es la casilla de la cuenta Resend. · usuario. Reemplaza la parte de QT-29 sobre `RESEND_FROM`/`RESEND_TO`. Consecuencia: verificar un dominio o cambiar de destinatario es un cambio de código, no de variable.
